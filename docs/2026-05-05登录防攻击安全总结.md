# 登录防攻击安全总结

> 日期: 2026-05-05
> 修改文件: `app/Http/Middleware/isLogin.php`

## 一、威胁模型

攻击者获取一个合法的 session cookie（注册账号登录即可获得），将其分发给大量 IP（肉鸡/代理池），同时并发请求需要登录的页面，耗尽数据库连接池。

### Laravel 原生认证流程（无防御）

```
Cookie → StartSession(Redis 读 session) → isLogin[auth()->guest()]
                                                ↓
                                        SessionGuard::user()
                                          ① $session->get() → Redis 取 user_id
                                          ② retrieveById()  → SELECT * FROM user WHERE id = ?
                                        ↓
                                      Controller 执行
```

**问题**: `auth()->guest()` 内部将 Redis 验证和数据库查询合并执行，无法在中间插入拦截逻辑。1000 个并发请求 = 1000 次 SELECT 查询。

### Laravel 原生能力的局限性

- `AuthenticateSession` 中间件：只检查密码是否被修改，不检查 IP
- Session 配置项（`secure`, `http_only`, `same_site`）：都是 Cookie 传输层保护，不防 session 被多 IP 使用
- Laravel session 设计哲学是"Cookie 即身份"，不感知 IP

## 二、防御方案

在 `isLogin` 中间件中，将认证流程拆分为三个阶段，在 Redis 验证和数据库查询之间插入 IP 限制检查。

### 修改后的认证流程

```
请求进入 isLogin
  ↓
① session->get() 从 Redis 取 user_id（0 次 DB 查询）
  → 无 user_id → 跳登录（结束）
  ↓
② checkSessionIpLimit() Redis IP 限制检查（0 次 DB 查询）
  → 超限 → 踢下线（结束）
  ↓
③ auth()->guest() 此时才触发数据库查询
```

### IP 限制算法

使用 Redis Set 记录每个 session 使用的 IP 集合：

```
Key:   session_ips:{session_id}
Value: Redis Set {ip1, ip2, ...}
TTL:   600 秒（10 分钟）
限制:   单 session 最多 5 个不同 IP
```

流程：

```
SADD session_ips:{sid} {ip}
  ↓
返回值 == 1（新 IP）?
  → 是: SCARD 检查数量
      → > 5: DEL 集合 + flush session → 踢下线
      → ≤ 5: EXPIRE 刷新 10 分钟 TTL
  → 否（旧 IP）: 跳过
```

### 为什么不用 auth()->logout()

`SessionGuard::logout()` 内部会执行：
1. `$this->user()` → `SELECT * FROM user WHERE id = ?`（读数据库）
2. `cycleRememberToken()` → `UPDATE user SET remember_token = ?`（写数据库）

在攻击场景下，每次踢出都触发 2 次数据库操作，违背了在数据库前拦截的初衷。

替代方案：`$request->session()->flush()` 只清空内存中的 session attributes，由 `StartSession::terminate()` 在请求结束时自动将空数据写回 Redis，覆盖原登录态。全程零数据库操作。

### Redis 操作开销

| 场景 | Redis 操作 | 数据库操作 |
|---|---|---|
| 旧 IP 正常请求 | 1 次 SADD | 1 次 SELECT |
| 新 IP 加入（≤5） | SADD + SCARD + EXPIRE | 1 次 SELECT |
| 第 6 个 IP（踢出） | SADD + SCARD + DEL | **0 次** |
| 已踢出的 session 后续请求 | 0 次（session 无 user_id 直接跳过） | **0 次** |

### 攻击效果对比

| 阶段 | 1000 个并发请求 | 数据库查询次数 |
|---|---|---|
| 无防御 | 全部到达控制器 | 1000 次 |
| 有 IP 限制 | 只有前 5 个到达控制器 | **5 次** |

## 三、关键设计决策

### session key 的计算

Laravel 存储登录状态的 key 格式为 `login_web_` + `sha1(SessionGuard 类名)`。手动从 session 读取此 key 可以验证 Redis 中 session 是否有效，绕过 `auth()->guest()` 的合并逻辑。

### EXPIRE 策略

每次有新 IP 加入 Set 时都刷新 600 秒 TTL。效果：
- 活跃用户：只要有新的正常 IP 加入，窗口持续延长
- 攻击者：被踢出后 Set 被 DEL 清除，即使重试也无法复用

### flush() 而非手动删 Redis session key

不硬编码 Redis session key 前缀（`ssrpanel_cache:`），而是依赖 Laravel 框架的 `session()->flush()` + `StartSession::terminate()` 机制自动回写空数据，避免与框架内部的 key 命名耦合。
