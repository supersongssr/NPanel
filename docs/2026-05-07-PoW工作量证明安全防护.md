## 1. 背景与目标

为防止 CC 攻击对登录、注册、密码找回、邮箱验证码等未认证 POST 端点的暴力请求，实施了 **Hashcash 风格的平滑型 PoW (Proof of Work) 工作量证明** 机制。

核心思路：每次 POST 请求前，浏览器必须完成一定量的 SHA-256 计算来证明其不是低成本的自动化脚本。

---

## 2. 架构设计

```
浏览器                                  服务器
  │                                       │
  │  1. 页面加载 → POST /auth/pow-challenge│
  │  ────────────────────────────────────> │
  │  <──── {timestamp, salt, difficulty,   │
  │         signature} (HMAC签名)          │
  │                                       │
  │  2. Web Worker 后台计算 SHA-256        │
  │     寻找 nonce 使 hash(salt+nonce)     │
  │     前6位hex ≤ 16777215/difficulty     │
  │                                       │
  │  3. 表单提交 (带 _pow_nonce 等字段)    │
  │  ────────────────────────────────────> │
  │      后端校验:                         │
  │      - 时效 (< now, ≤ 15min)          │
  │      - HMAC 签名                       │
  │      - SHA-256 工作量                  │
  │      - Redis SETNX 防重放             │
  │                                       │
  │  4. 自动请求新 challenge 重算          │
  │  ────────────────────────────────────> │
```

### 2.1 动态难度

```
difficulty = base_difficulty + sys_getloadavg()[0] × 160000
```

- `base_difficulty`: 数据库 `config` 表 `pow_base_difficulty` 行，默认 10000
- 负载越高，难度越大，自动调节计算成本
- 正常负载下约需浏览器 0.5~2 秒完成计算

### 2.2 防护覆盖端点

| 端点 | 提交方式 | PoW 集成方式 |
|------|----------|-------------|
| `POST /login` | 表单 POST | `PoW.consume()` → 注入隐藏字段 |
| `POST /register` | 表单 POST | `PoW.consume()` → 注入隐藏字段 |
| `POST /resetPassword` | 表单 POST | `PoW.consume()` → 注入隐藏字段 |
| `POST /sendCode` | AJAX POST | `PoW.consumeForAjax()` → 参数合并 |
| `POST /auth/pow-challenge` | AJAX POST | 无需 PoW (challenge 本身) |

## 4. 安全机制详解

### 4.1 Challenge 签名

```
signature = HMAC-SHA256(IP|timestamp|salt|difficulty, APP_KEY)
```

- 绑定客户端 IP，challenge 不可跨 IP 使用
- 使用 Laravel `APP_KEY` 作为 HMAC 密钥
- `hash_equals()` 时序安全比较防时序攻击

### 4.2 工作量验证

```
hash = SHA-256(salt + nonce)
valid = hexdec(hash[0:6]) ≤ floor(16777215 / difficulty)
```

- "平滑型" 难度：不要求固定前导零，而是整数阈值比较
- difficulty=10000 → threshold=1677 → 约 1/1677 概率命中
- difficulty=100000 → threshold=167 → 约 1/100000 概率命中

### 4.3 防重放

```
Redis SET NX EX pow:{sha256_hash} 1 900
```

- 原子操作：同一 hash 只能写入一次
- 900 秒 (15分钟) TTL 自动过期
- 同一 nonce 不可重复使用

### 4.4 时效校验

- timestamp 必须 **严格小于** 当前时间 (防未来时间)
- 距当前时间不超过 900 秒 (15 分钟有效期)

## 5. 前端技术要点

### 5.1 Inline Web Worker

```javascript
var blob = new Blob([WORKER_SRC], {type: 'application/javascript'});
var worker = new Worker(URL.createObjectURL(blob));
```

- 不需要额外 JS 文件
- Blob URL Worker 在 HTTPS 环境继承 Secure Context，crypto.subtle 可用
- Worker 创建包裹 try-catch，浏览器不支持时优雅降级

### 5.2 crypto.subtle.digest

```javascript
crypto.subtle.digest("SHA-256", buffer).then(function(hashBuf) {
    // 异步，不阻塞
});
```

- 浏览器原生 API，无需第三方库
- 返回 Promise，配合 Promise.all 批量处理
- 每批 256 个 nonce，完成后 setTimeout(runBatch, 0) 让出 UI 线程

### 5.3 生命周期管理

```
页面加载 → PoW.init() → POST challenge → Worker 计算
                                    ↓
用户提交表单 → PoW.consume() → 注入字段 → 表单提交 → 自动请求新 challenge
```

多 POST 场景 (register 页面有 sendCode + register 两个 POST):
- `consumeForAjax()`: 用于 AJAX 调用，返回参数对象
- `consume()`: 用于表单提交，注入隐藏字段
- 每次消费后自动重算下一个 challenge

## 6. 修复过程中遇到的问题

### 6.1 CSRF 419 错误
- **问题**: 初始 pow.js 用 `Content-Type: application/json` 发送请求未带 CSRF token
- **修复**: 改为 `application/x-www-form-urlencoded`，从 DOM 读取 `_token` 参数

### 6.2 WORKER_SRC_SYNC 违规
- **问题**: QA 审查发现 `createWorker()` 使用了包含纯 JS 同步 SHA-256 的 `WORKER_SRC_SYNC`
- **修复**: 完全重写 pow.js，仅保留使用 `crypto.subtle.digest` 的 `WORKER_SRC`

### 6.3 Laravel 日志权限
- **问题**: 以 root 执行 `artisan migrate` 后日志文件属主为 root，PHP-FPM (www-data) 无法写入
- **修复**: `chown www-data:www-data storage/logs/laravel-*.log`

### 6.4 Redis Facade 命名冲突
- **问题**: `isLogin.php` 的 `use Redis;` 解析为 PHP 原生 Redis 扩展而非 Laravel Facade
- **修复**: `use Illuminate\Support\Facades\Redis;`

### 6.5 register sendVerifyCode 异步竞态
- **问题**: 原 `async: false` + `flag` 变量模式在改为异步后，倒计时在 AJAX 完成前启动
- **修复**: 倒计时移入 AJAX success 回调，修正为 60 秒

## 9. 后续优化建议
