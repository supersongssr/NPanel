# 工单提交频率限制方案

> 日期：2026-05-07
> 分支：fix/del-ticket-cost-money-fuck-del-it

## 问题分析

### 当前状态：无任何频率限制

工单提交入口 `POST /addTicket` 和 `POST /replyTicket` **没有任何速率限制**。

- 路由层 (`routes/web.php:121-125`)：仅用 `isLogin` 中间件验证登录
- Controller 层 (`UserController.php:412-452`)：仅验证标题/内容非空，无频率检查

**风险**：恶意用户可循环调用 `POST /addTicket`，向 `ticket` 表灌入大量垃圾数据。

---

## 方案：Controller 内 Redis 计数（最简）

**只改 1 个文件：`app/Http/Controllers/UserController.php`**

### 限制值

| 操作 | 限制 | Redis Key |
|------|------|-----------|
| 创建工单 | 3 次/小时/用户 | `ticket_create:{userId}` |
| 回复工单 | 10 次/小时/用户 | `ticket_reply:{userId}` |

### 改动内容

1. 顶部加 `use Illuminate\Support\Facades\Redis;`
2. `addTicket()` — 验证通过后、创建工单前加 Redis 检查
3. `replyTicket()` — POST 分支内，验证通过后、创建回复前加 Redis 检查

### Redis 逻辑（每个方法 3 行）

```
INCR key → EXPIRE key 3600 → 如果值 > 阈值则返回错误
```

每次 INCR 后都执行 EXPIRE（不判断 count === 1），确保 key 始终有 TTL，避免进程崩溃导致 key 无过期时间、永久锁死用户。

### 响应格式

前端使用 jQuery `$.post()` + `layer.msg(ret.message)` 处理响应，**必须是 HTTP 200 + JSON**：

```json
{"status": "fail", "data": "", "message": "工单提交过于频繁，请稍后再试"}
```

不能用 HTTP 429 / 302 / 其他状态码——`$.post()` 的 success 回调只处理 HTTP 200，非 200 进入 error 回调，前端不会显示任何提示。

此格式与 Controller 中所有现有的错误返回格式完全一致（参见 `addTicket` 的 `请输入标题和内容`、`replyTicket` 的 `回复内容不能为空` 等响应）。

### 不做的事

- 不建新中间件
- 不改路由 / Kernel
- 不加 IP 维度（后续需要可再加）
- 不加最大未关闭工单数检查
- 不改前端

---

## QA 审查要点

### 竞态条件：INCR/EXPIRE 非原子

INCR 和 EXPIRE 是两条独立的 Redis 命令。理论上，如果 INCR 返回后 PHP 进程在 EXPIRE 之前崩溃，key 会失去 TTL。

**应对策略**：每次 INCR 后无条件执行 EXPIRE。代价是每次请求多一次 Redis 调用（微秒级），但保证：
- 即使某次 EXPIRE 漏执行，下一次请求会补上 TTL
- 不会出现永久无 TTL 的 key
- 不需要引入 Lua 脚本或 pipeline 的额外复杂度

### Redis 故障

Redis 不可用时 `Redis::incr()` 会抛异常，当前未做 try/catch——Redis 故障将导致工单提交直接报错。这是可接受的降级行为（比无限刷单安全）。

---

## 验证方式

1. 连续快速提交 4 次工单 → 第 4 次应返回 `{"status":"fail","message":"工单提交过于频繁..."}`，前端 layer.msg 弹出提示
2. 连续快速回复 11 次 → 第 11 次应返回 `{"status":"fail","message":"回复过于频繁..."}`
3. 等 1 小时后 key 过期，应恢复正常
4. 管理员工单操作不受影响（不同 Controller / 路由组）
