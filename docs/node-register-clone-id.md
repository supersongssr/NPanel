# NPanel 节点注册与克隆 ID 分配逻辑报告

## 1. 误区说明
关于用户提到的 `public/js/wangEditor/.../registerServiceWorker.js`：该文件是第三方编辑器 wangEditor 的 React 示例代码，用于处理浏览器的 Service Worker 缓存，**与 NPanel 的节点注册、克隆或 ID 获取逻辑完全无关**。

NPanel 的节点注册与 ID 分配完全由后端 **`NodeApiController@register`** 方法驱动。

## 2. 核心逻辑：节点裂变 (Fission) 与克隆分配
当一个主节点（Main Node）发起 `/api/node/register` 请求时，后端会根据其协议配置和 IP 类型，将其“裂变”为多个子节点。

### A. 需求计算
1. **协议展开**：通过 `expandProtocols` 将 `v2_name`（如 `xhttp-hy2-ws-grpc`）拆分为独立的协议列表。
2. **IP 组合**：检查节点拥有的 IPv4 和 IPv6 地址。
3. **槽位生成**：构建“协议 × IP”的任务槽位（Slots）。例如：4个协议 × 2个IP = 8个槽位。

### B. ID 获取与重用机制 (核心)
后端采用 **“重用与回收优先，按需新增”** 的策略来分配子节点 ID：

1. **优先级 1：重用与缩减既有克隆**：
   ```php
   $existingClones = SsNode::where('is_clone', $nodeId)->get()->values();
   ```
   - **重用**：系统会优先复用属于该主节点的旧记录。
   - **缩减 (Recycle)**：如果由于配置变更（如协议减少），实际需求的槽位少于既有的克隆数，多余的节点将**不再被物理删除**。系统会将其 `is_clone` 设为 `0` 且 `status` 设为 `0`（下线），将其释放到公共池中，等待 32 天冷却后被回收重用。

2. **优先级 2：回收“死亡”节点 (Recycle)**：
   如果既有克隆不足以满足槽位需求，系统会搜索 **“超过 32 天没有心跳”** 的节点（包括由于过期或停用被遗弃的旧节点）。
   - **判定标准**：`heartbeat_at < 32天前` 或 `(heartbeat_at 为空 且 created_at < 32天前)`。
   - **分配原则**：按照 `heartbeat_at` 降序排列，优先回收最近刚“死掉”的节点。
   - **清理**：在回收 ID 时，系统会自动清除该 ID 关联的所有旧 DNS 解析记录，确保新节点拥有干净的环境。

3. **优先级 3：新增 (Create)**：
   如果没有任何可重用或可回收的节点，系统才会新建 `SsNode` 记录并由数据库分配全新的自增 ID。

### C. ID 序列封存
最后，系统将所有（主节点 + 克隆节点）的 ID 汇总，并存入主节点的 `node_ids` 字段。

## 3. 为什么会获得看似“随机”的 ID？
由于引入了回收机制，新申请 ID 的表现如下：
- **`applyId` 阶段**：如果你申请新 ID，系统会先看有没有 32 天没心跳的“废弃 ID”。如果有，你会拿到一个旧的编号（例如 1089），而不是当前最大 ID + 1。
- **首次裂变**：克隆节点也会优先占用那些长期不活跃的坑位。
- **稳定性**：一旦 ID 被分配给你的主节点或作为其克隆，只要你保持心跳，这些 ID 就不会被别人抢走。

## 4. 结论
节点获得 ID 的途径包括 **“数据库自增”** 和 **“32天失效节点回收”**。回收机制能有效压缩 ID 空间，避免数据库主键无限膨胀，同时提高了旧资源的利用率。系统在回收时会确保数据清理，对用户业务无感知。
